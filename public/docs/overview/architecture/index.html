    Architecture

    Rift Wallets has one rule that shapes every component: the only thing that can authorise a fund movement is a signature from one of the customer’s passkeys, checked on-chain by their Safe. Everything else carries that signature or prepares the operation it signs.

    The pieces

    Section titled “The pieces”

    Your app calls Rift over HTTPS with your project API key and, for customer operations, the customer’s access token. Server-side code never signs anything: it either forwards a passkey proof the customer produced, or gets an approval request back.

    Widget and SDKs run the WebAuthn ceremonies. The hosted widget (embed.js, <RiftAuth>, <RiftApprove>) runs them inside a Rift iframe under Rift’s relying party. @rift-finance/wallet exposes createPasskeyAuthProof() and registerPasskey() when you run them on your own domain.

    Customer device holds the passkey. The private key is created and kept in the authenticator (Secure Enclave, Android keystore, TPM or a security key) and may sync through iCloud Keychain or Google Password Manager. It never reaches Rift.

    Rift API handles sign-in, builds two-phase signing tickets, stores approval requests, routes payouts and onramp to the right local rail and records every transaction in the ledger. Before submitting, it verifies the WebAuthn assertion off-chain (P-256 over the authenticator data and client data hash, challenge equal to the ticket’s hash, credential belongs to the customer) so a bad signature fails fast with 400 INVALID_PASSKEY_SIGNATURE.

    smart-wallet is Rift’s ERC-4337 service. It builds the Safe UserOperation, computes the hash the passkey must sign (the Safe4337Module EIP-712 SafeOp hash), and encodes the WebAuthn signature into the UserOperation’s signature field.

    Bundler and paymaster submit the UserOperation. The paymaster either sponsors gas or takes it from the Safe in USDC/USDT. See gas sponsorship.

    Chain. The Safe (v1.4.1 with the Safe4337Module, EntryPoint v0.7) validates the operation. Its owner is a Safe WebAuthn signer contract that verifies the P-256 signature through the RIP-7212 precompile, with the FCL Solidity verifier as fallback. A request without a valid passkey signature does not execute.

    One transfer, step by step

    Section titled “One transfer, step by step”
    1. Preview. Your app posts { token, chain, recipient, amount } to POST /v1/transactions/preview. Rift builds the UserOperation and returns { ticketId, hashToSign, allowCredentials, expiresAt }. Nothing is signed.
    2. Passkey. The device signs hashToSign (the 32 raw bytes are the WebAuthn challenge, user verification required). The result is an authProof.
    3. Submit. Your app posts { ticketId, authProof } to POST /v1/wallet/user-operations/submit-prepared. Rift verifies the assertion, smart-wallet encodes it and the bundler submits.
    4. Verify on-chain. The Safe checks the passkey signature and executes.

    When the operation starts on a server instead, step 1 becomes 202 APPROVAL_REQUIRED and steps 2 to 4 happen on the approval page. See two-phase signing and approvals.

    Addresses and deployment

    Section titled “Addresses and deployment”

    The Safe address is counterfactual: it is derived from the customer’s first passkey and is the same on every supported chain. The Safe is deployed on a chain by the first operation there, signed by that passkey. When it deploys, the same operation adds every other active passkey as an owner, so later prompts work with any of them.

    Customers who had a wallet before passkeys keep their address: on first use of each chain, the old owner key is swapped out for their passkeys in one operation, and is never used for anything else.
