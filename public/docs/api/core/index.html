    Overview

    What is in this reference. Endpoints you call with your project API key or a project id you own, the server-only platform tier (psk_ key), and public reference data. End-user flows that the Rift widget, React components and SDK run for you are collected under Used by the Rift widget and app.

    Rift Finance API 2.0.0

    Section titled “Rift Finance API 2.0.0”

    The Rift Finance backend.

    Passkey-owned wallets. Every user wallet is a Safe owned only by the user’s passkeys (WebAuthn P-256). Signatures are produced on the user’s device and verified on-chain by the Safe — Rift’s servers hold no key that can move user funds. Existing wallets keep their address (owner swap from the old key to the user’s passkeys, per chain, on first use).

    Two-phase signing. Every fund-moving or signing operation is preview → passkey signs hashToSign → submit { ticketId, authProof }.

    Approval requests. One-phase routes called without a passkey proof (API key + user JWT, SDK, MCP) return 202 APPROVAL_REQUIRED with an approvalUrl the user opens to approve with a passkey.

    Login. Sign-in (OTP / password / Google / Apple) provisions no keys and returns walletStatus; when needsPasskeySetup is true the user must register a passkey before signing (409 PASSKEY_SETUP_REQUIRED). Google / Apple are login only.

    Used by the Rift widget and app

    These operations are the end user's own flows. They are authenticated with the customer's access token (not your project key) and are run for you by the widget, the React components and the SDK. You normally do not call them yourself. They are not part of the per-project API above.

    • POST /v1/auth/sessions/refresh Rotate the refresh-cookie and issue a fresh access JWT.
    • POST /v1/auth/sign-out Revoke the refresh-cookie.
    • GET /v1/me Get the authenticated user's profile.
    • PUT /v1/me Update the authenticated user's profile (PUT alias of PATCH).
    • PATCH /v1/me Update the authenticated user's profile.
    • DELETE /v1/me Delete the authenticated user and all related data.
    • GET /v1/me/tokens List the tokens currently owned by the authenticated user.
    • GET /v1/balances Get all token balances on a given chain or across all chains.
    • GET /v1/balances/tokens/{symbol} Get the balance of a specific token across chains.
    • GET /v1/transactions List the user's transaction history.
    • POST /v1/transactions Send tokens across chains (native or ERC-20).
    • GET /v1/transactions/fee-estimate Estimate the on-chain fee for a transfer (paymaster-aware).
    • GET /v1/wallet/identity Get wallet identity (EOA address). The public key is dropped in Phase 2 — derive it from any signature if you need it.
    • POST /v1/wallet/chains/{chain} Get wallet instance metadata for a specific chain.
    • POST /v1/wallet/signatures/message ERC-1271 message signing, phase 2 → { signature } (ERC-6492-wrapped if the Safe is undeployed).
    • POST /v1/wallet/user-operations Send an ERC-4337 user operation via the smart-wallet service.
    • POST /v1/wallet-connect/pairings Pair the wallet with a DApp via a WalletConnect URI.
    • GET /v1/wallet-connect/requests List pending WalletConnect requests awaiting approval.
    • POST /v1/wallet-connect/requests/{id}/approve Approve a pending WalletConnect request.
    • POST /v1/wallet-connect/requests/{id}/reject Reject a pending WalletConnect request.
    • GET /v1/wallet-connect/sessions List active WalletConnect sessions.
    • DELETE /v1/wallet-connect/sessions/{topic} Disconnect a WalletConnect session.
    • GET /v1/bridge/routes List supported bridge routes and tokens.
    • POST /v1/bridge/quotes Get a crosschain bridge quote with platform-fee + balance check.
    • POST /v1/bridge/transfers Execute a crosschain bridge transfer via Rift's bridge.
    • GET /v1/invoices/{id}/redirect Public redirect to the invoice URL (used by short-link surfaces).
    • GET /v1/merchants/{id} Get a merchant's approval status.
    • POST /v1/kyc/sessions Create a KYC verification session (Rift picks the verification flow by country).
    • GET /v1/kyc/status Check the authenticated user's KYC verification status.
    • POST /v1/kyc/status Look up a user's KYC verification status by identifier.
    • POST /v1/kyc/poll-and-notify Poll a KYC job to completion and dispatch a one-time code on success.
    • POST /v1/kyc/submissions Submit KYC images (from frontend or via server-to-server).
    • GET /v1/kyc/jobs/{jobId} Poll a KYC submission job to completion.
    • GET /v1/offramps List the user's offramp orders (newest first, paginated).
    • POST /v1/offramps Pay out stablecoins to local money (one-phase).
    • GET /v1/offramps/{transactionCode} Payout order by Rift order id (or, for older orders, by transaction code).
    • GET /v1/deposits List the user's onchain deposits.
    • GET /v1/deposits/stats Get the user's deposit statistics.
    • GET /v1/projects List projects owned by the authenticated user.
    • POST /v1/projects Create a new project (bootstrap; OTP required).
    • DELETE /v1/projects/{id} Delete a project.
    • POST /v1/notifications/messages Send a notification email to the authenticated user (self).
    • POST /v1/notifications/broadcasts Project owner broadcasts an email to every user in their project.
    • POST /v1/wallet/user-operations/preview Phase 1 — build an ERC-4337 UserOperation and return the hash + ticket to sign.
    • POST /v1/wallet/user-operations/submit-prepared Phase 2 — submit a previously-previewed UserOperation with the user's authProof.
    • POST /v1/transactions/preview Phase 1 of a v3 token transfer — returns the UserOp hash + ticket for a `token / recipient / amount` triple.
    • POST /v1/offramps/preview Phase 1 of a v3 off-ramp — builds the ERC-20 transfer to Rift's settlement address and returns hash + ticket.
    • POST /v1/bridge/transfers/preview Phase 1 of a v3 cross-chain bridge — builds the bridge calls and returns hash + ticket.
    • POST /v1/offramps/init Two-phase payout, step 1: create the order and return the hash to sign.
    • POST /v1/offramps/finalize Two-phase payout, step 2: submit the passkey signature and start the fiat leg.
    • POST /v1/wallet-connect/requests/{id}/preview Phase 1 for a v3 WalletConnect approval — build the UserOp for the dApp's request and return hash + ticket.
    • GET /v1/wallet/status Passkey-wallet status (also returned as `walletStatus` by every sign-in).
    • POST /v1/wallet/passkeys/options WebAuthn registration options (ES256 only, 32-byte single-use challenge, 5 min).
    • GET /v1/wallet/passkeys List the user's passkeys.
    • POST /v1/wallet/passkeys Register a passkey (creates, migrates or extends the wallet).
    • POST /v1/wallet/passkeys/confirm Confirm an added passkey with signatures from an existing passkey (one per deployed chain).
    • DELETE /v1/wallet/passkeys/{id} Start removing a passkey (removeOwner tickets for every deployed chain).
    • POST /v1/wallet/passkeys/{id}/confirm-removal Submit the passkey-signed removeOwner tickets.
    • GET /v1/approvals List the user's approval requests (app inbox).
    • GET /v1/approvals/{id} Get an approval request — owner user JWT, or the creating project's API key alone.
    • POST /v1/approvals/{id}/preview Fresh two-phase ticket built from the stored intent.
    • POST /v1/approvals/{id}/approve Approve with the passkey-signed ticket from /preview (single use).
    • POST /v1/approvals/{id}/reject Reject an approval request.
    • POST /v1/wallet/signatures/message/preview ERC-1271 message signing, phase 1 (personal_sign or typed data).
    • GET /v1/onramps/quote Quote a fiat amount.
    • GET /v1/onramps/kyc Whether the customer's verified KYC is usable for onramp (no personal data returned).
    • GET /v1/onramps The user's onramp orders.
    • POST /v1/onramps Buy stablecoins into the customer's own Safe.
    • GET /v1/onramps/{id} One onramp order with its current status.
    • GET /v1/beneficiaries Saved recipients (most recently used first).
    • POST /v1/beneficiaries Save a recipient. Fiat recipients get a name lookup; deduped on (type, identifier, bankCode).
    • PATCH /v1/beneficiaries/{id} Edit label / network / bank name (identifier is immutable).
    • DELETE /v1/beneficiaries/{id} Delete a saved recipient.
    • GET /v1/ledger Every money movement of the user, newest first.
    • POST /v1/statements/challenge Single-use (5 min) passkey challenge for a statement.
    • POST /v1/statements Statement (CSV or PDF) authorised by a passkey assertion over hashToSign; emailed or downloaded.
    • GET /v1/devices List devices
    • POST /v1/devices Register this device's key
    • GET /v1/devices/policy Enforcement switch
    • POST /v1/devices/{id}/approve/challenge Passkey challenge to approve a pending device (from a trusted device)
    • POST /v1/devices/{id}/approve Approve a pending device with a passkey (from a trusted device)
    • POST /v1/devices/{id}/recover/start Lost other device: send an OTP (from the pending device itself)
    • POST /v1/devices/{id}/recover/verify Verify the OTP → cooling_off
    • POST /v1/devices/{id}/recover/cancel Cancel link from the email (no JWT)
    • DELETE /v1/devices/{id} Remove a device (from a trusted device)
    • POST /v1/offramps/{id}/refund Refund a failed payout to the customer's wallet.
    • GET /v1/identifier-recovery/methods Get the authenticated user's recovery methods.
    • POST /v1/identifier-recovery/methods Create the authenticated user's recovery methods.
    • PUT /v1/identifier-recovery/methods Replace all of the authenticated user's recovery methods.
    • DELETE /v1/identifier-recovery/methods Delete all of the authenticated user's recovery methods.
    • POST /v1/identifier-recovery/methods/{type} Add a specific recovery method.
    • PATCH /v1/identifier-recovery/methods/{type} Update the value of a specific recovery method.
    • DELETE /v1/identifier-recovery/methods/{type} Remove a specific recovery method (cannot remove the last one).

    Security scheme type: apiKey

    Header parameter name: X-Admin-Key

    platformKeyAuth

    Section titled “platformKeyAuth”

    Rift Wallets platform secret key (psk_…). Also accepted as Authorization: Bearer psk_…. Server-to-server only; the project sk_ key is NOT accepted. Dashboard alternative: owner session bearer token + X-Project-Id (session user must own the project, else 403). A key with a differing X-Project-Id -> 403. 60 requests/minute per key.

    Security scheme type: apiKey

    Header parameter name: X-API-Key
